# Frozen matched taste experiment

Status: brief content frozen before skill implementation; no trial has run. The six SHA-256 content hashes and held-out flags are in briefs/manifest.json. Do not modify a brief after this freeze. If a factual impossibility is discovered, record the issue and invalidate that trial rather than silently replacing it.

## Arms and isolation

Run six matched pairs, one plain baseline and one treatment with the new broad reference-driven taste skill. Add the popular frontend-design skill as a third arm for B04 only, recording its exact upstream source, commit/version and hash before execution. This creates thirteen initial artifacts. If that comparator cannot be obtained, report the missing comparator and do not substitute an unrelated skill under its name.

The implementation agent may read B01–B04 and this protocol. It must not read B05, B06, critic-references.md, or future trial artifacts until the candidate skill has been frozen and hashed. The coordinator must enforce this through explicit scoped handoff, not assume file visibility is access control. Record whether any leakage occurs; held-out claims become invalid if it does. Keep held-out trials out of skill repair feedback until the final candidate is selected.

Use fresh isolated agent contexts per artifact, no inherited implementation conversation, no other arm's artifact or critique, and the identical brief verbatim. Same model, reasoning effort, tool set, build time or token budget, dependency availability, output format, and acceptance checks in all arms. Record actual configured model and effort; do not infer defaults. All arms may independently research external examples. The only intended difference is the injected skill. Baselines receive ordinary competent artifact-production instructions, including permission to research and verify. No baseline weakening or treatment-only rendering tools.

Predeclare an equal per-artifact budget before starting. Balance run order across pairs with a recorded randomized assignment. Do not present the skill name in artifacts or critic packets. Keep provenance and tool logs outside rendered deliverables. Any common environment fix must be available equally to every arm affected.

## Artifact evidence and blind assessment

Each run saves the actual index.html, sources.txt, rendered desktop/mobile screenshots, and a concise observed-check log generated by an independent verifier. Interactions receive a short interaction recording or sequence of screenshots proving the required transitions. Inspect timed work over its full duration and print work at actual scale in a print preview/PDF; record any physical construction limit candidly. Static screenshot quality cannot establish functional completion.

A coordinator assigns opaque random artifact labels and strips arm metadata from review packets. Critics receive the original brief, anonymous artifacts/screenshots, required test evidence, and critic-only external exemplar locations. They do not receive maker self-assessments, the skill, arm names, or claimed improvements. Use at least two independent critics in fresh contexts. Ask them first to describe what they can actually see or do, then identify precise strengths, failures, and applicable external craft standards. Require concrete references to artifact elements, not generic adjectives.

No numeric scoring. For each pair, critics give a supported preference, indistinguishable, or mixed, explaining task fit, expression, clarity, structure, interaction/sequence when relevant, and construction reliability. A visually preferred artifact with broken required behavior is recorded as such. Preserve disagreement instead of averaging it away. Report cross-task patterns and limitations; six pairs are a bounded experiment, not proof of universal quality.

## Targeted repairs and stopping

Allow at most three targeted skill repair rounds. Each must name a recurring observed failure on B01–B04, modify the smallest relevant skill guidance, freeze a new skill hash, and rerun affected development pairs with fresh contexts and equal budgets in both arms. Preserve all previous outputs and critiques. Do not choose only favorable reruns or expand scope opportunistically. Comparator B04 remains tied to its frozen skill version; if B04 is rerun, rerun the comparator under the same budget.

Choose the final candidate using development evidence, then run B05 and B06 once as untouched held-out pairs. No skill edits or reruns justified by held-out critique. Final reporting includes all initial and repaired development results, both held-out results, comparator result, actual cost/time evidence if available, functional failures, critic disagreement, and whether isolation held. Stop after the selected candidate's held-out evaluation or after the third repair round followed by held-out evaluation. Do not run trials as part of this freezing step.
